# Decision Log

## Decision #01 — 제품 방향 피벗: MD 발주 도구 → Consumer Trend Intelligence

문제: 기존 구현은 "패션 MD 실무 도구"(트렌드 스캐너 + 상품 태거 + 스타일보드 + 발주 플래너)였으나,
지원 목적은 "연령·성별 검색 관심 → 시각적 스타일 레퍼런스"를 탐색하는 소비자용 서비스 증명이었다.

결정: 기존 UI 시각 언어(레이아웃/컬러/카드/타이포/Radar 스타일/네비게이션)는 유지하되, 상품 태거·
스타일보드·발주 플래너 화면과 API는 제거하고 Home(성별·연령·기간 선택) → Trend(Rising/Stable/
Falling) → Trend Detail(관련 키워드 + 시각 레퍼런스) 흐름으로 재설계했다.

이유: 두 제품을 한 앱에서 동시에 유지하면 정보구조가 뒤섞여 어느 쪽도 포트폴리오 스토리로 설명하기
어려워진다.

## Decision #02 — 연령 구간은 API가 실제로 지원하는 값을 그대로 쓴다

문제: 기획서 예시는 18–19/20–24/25–29/30–34 구간을 제시하지만, NAVER 검색 트렌드 API의 실제 연령
코드는 13–18/19–24/25–29/30–34/35–39다.

결정: 기획서 예시 구간이 아니라 API가 실제로 제공하는 구간을 그대로 노출한다.

이유: 데이터 품질 규칙 #1, #6 — 실제 API에서 제공하지 않는 구간을 임의로 만들어내지 않는다.

## Decision #03 — Pinterest 이미지는 딥링크 + NAVER 이미지로 대체(임시)

문제: Pinterest Trends API는 키워드 성장률만 제공하고 이미지 검색은 별도 승인 범위가 필요하다.
승인 신청은 진행 중이나 승인 여부·소요 시간이 불확실하다.

결정: 승인 전까지는 (1) 공식 Pinterest 검색 페이지 딥링크(스크래핑 없음), (2) 이미 승인된 NAVER
이미지 검색 결과를 "NAVER 이미지 검색 기반 · Pinterest 연동 전 임시"로 명확히 라벨링해 함께
보여준다. 승인 후에는 VisualSignal 컴포넌트의 `status === "live"` 분기만 채우면 되도록 인터페이스를
미리 맞춰 뒀다.

이유: 데이터 품질 규칙 #1(생성 금지), 7.2(스크래핑 금지)를 지키면서도 앱이 "빈 화면"이 아니라
실제로 동작하는 상태를 유지하기 위함.

## Decision #04 — raw_search_trend 에는 live 데이터만 적재한다

결정: `search.status === "live"`일 때만 Supabase에 insert 한다. 데모/실패 폴백 데이터는 DB에
전혀 쓰지 않는다.

이유: raw_search_trend는 "원본 그대로 보존"이 원칙인 테이블이다. 데모 데이터가 섞이면 나중에
어떤 행이 진짜 API 응답인지 구분할 수 없어진다.

## Decision #05 — Supabase 연결은 스키마 준비 + best-effort persistence로 우선 진행

문제: 실제 Supabase 프로젝트 생성·인증은 에이전트가 대신 할 수 없다(대시보드 계정, 인터랙티브
OAuth 필요).

결정: `supabase/migrations/0001_init.sql`로 스키마를 준비하고, `lib/supabase.ts` + `trend-db.ts`의
persistence 로직을 env var(`SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`) 유무로 게이팅했다. 키가
없으면 조용히 스킵하고 인메모리 캐시로만 동작한다.

이유: 나머지 기능이 실제 프로젝트 생성 전에도 그대로 동작해야 한다. 프로젝트 생성 후 키만
넣으면 별도 코드 변경 없이 live 데이터 적재가 시작된다.
